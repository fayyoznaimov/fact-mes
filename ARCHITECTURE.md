# Архитектура MES цеха: как устроено и почему так

Коротко: язык и базу не меняем — и 13-го, и 14-го сентября узким местом
оказывался алгоритм, а не Python и не SQLite. «Узкие места» за всю историю
считались 28 секунд; после свёртки остановов — одна секунда, повторно — из памяти.
Под нагрузкой 30 мониторов и 10 человек с тяжёлыми отчётами приложение держит
412 запросов в секунду без ошибок, а доска доходит до всех мониторов за четверть
секунды. Переписывание на другой стек накануне подключения дало бы риск и ни
одной секунды выигрыша.

## Как это устроено в MES-системах

MES — средний уровень между станками и учётной системой (по ISA-95):

| Уровень | Что это | У нас |
|---|---|---|
| 0–1 | станок и его контроллер | Toyota JAT810 |
| 2 | сбор данных со станков | Toyota FACT: снимок раз в минуту, итоги смен, журнал остановов |
| 3 | MES: события, причины простоев, андон, план-факт, персонал | это приложение |
| 4 | ERP: заказы, техкарты, склад | 1С |

Во всех системах для ткацких цехов (LDS в Пакистане, Datalog, Loom Monitoring)
один и тот же цикл, и он у нас теперь замкнут:

1. **Станок встал** — событие приходит от сбора данных без участия людей.
2. **Короткий останов станок называет сам** (уток, основа, ворс) — это обрыв.
3. **Длинный останов объясняет человек**: в LDS — RFID-карта мастера у станка, у
   нас — тикет с монитора. Причина, которую никто не назвал, копится отдельной
   строкой «без причины».
4. **Андон**: стоящий без причины станок поднимается наверх доски, краснеет,
   уходит мастеру — пока причину не назовут.
5. **Отчёты**: КПД в трёх вариантах (Shed / Time / Prod), Парето причин,
   обрывность на 100 тысяч пиков, реакция и MTTR, план-факт по заказам.

## Как устроено у нас

```
Станки Toyota ──TMS──> FACT 172.0.30.9 (Apache: снимок раз в минуту, смены, остановы)
                          │
                          ▼  каждые 5 с — новый снимок? каждые 2 мин — новые смены и остановы
                   collector.py ──────────────> fact.db (SQLite): смены, остановы, свёртка stop_day
                     │   │
                     │   └──> run/live.json  (снимок станков для мониторов)
                     └──────> тикеты и андон ──> shop.db ──> телеграм мастеру
                                                   ▲
   20 мониторов тикетов ◄── /api/stream (толчки) ──┤
   10 отчётных экранов, компьютеры ◄── /api/… ─────┤  web.py, порт 8780
   1С (заказы, техкарты), бот, BI ◄──► /api/v1/… ──┘  вход по ключу
```

- **Сборщик — единственный, кто пишет в базу станков.** Раз в 5 секунд спрашивает
  FACT, нет ли нового снимка; FACT выкладывает его раз в минуту. Новый снимок —
  файл `run/live.json`, автотикеты, андон. Раз в две минуты забирает
  изменившиеся файлы смен и остановов (с `If-Modified-Since`: неизменившийся
  файл сервер FACT заново не отдаёт) и дописывает их в базу. По умолчанию живёт
  потоком внутри приложения; можно отдельным процессом — второй не запустится.
- **Толчки на мониторы** — Server-Sent Events: монитор держит одно соединение,
  сервер пишет в него доску, как только поменялся снимок или завели тикет. Доска
  собирается один раз на версию, двадцать мониторов получают одни и те же байты.
  Оборвалось соединение — страница сама переходит на опрос раз в 15 секунд.
- **Свёртка остановов `stop_day`** — остановы, сложенные по дню, станку, смене и
  причине, с гистограммой времени прихода оператора. Отчёты читают тысячи строк
  вместо миллионов, медиана реакции берётся из гистограммы. Сверено со старым
  расчётом: количество, минуты и MTTR совпадают до единицы, медианы — ±1 с.
- **Кэш «один считает, остальные ждут»** для тяжёлых отчётов: данные меняются раз
  в две минуты, а один и тот же отчёт открывают несколько человек сразу.
- **Внешний API `/api/v1/…`** — для 1С, бота и BI, вход по ключу (в базе только
  хэш), описание для программиста — `/api/docs`, машиночитаемое — OpenAPI.

если брать данные со станков в обход FACT.

## Язык, фреймворк, база

**Python и стандартная библиотека остаются.** Всё, ради чего стоило бы менять
стек, сделано на нём: толчки на мониторы, внешний API с описанием, фоновый сбор.
Ноль внешних зависимостей — нечему сломаться при обновлении, сервер ставится
копированием папки.

**FastAPI не понадобился.** В прошлой записке он был условием для толчков и API;
оба сделаны без него. Переходить имеет смысл, только если API станет большим
(десятки внешних потребителей).

**База — SQLite в режиме WAL.** Один пишущий (сборщик), десятки читающих — ровно
тот случай, на который она рассчитана. Поправка к прошлой записке: при 80 станках
остановов будет не 700 тысяч, а около **8 миллионов в год** (сейчас 11 тысяч в
сутки на 40 станках) — порядка гигабайта в год. Это по-прежнему немного: отчёты
читают свёртку, а не сырые остановы.

**MS SQL — когда понадобится второй сервер или прямой доступ 1С к базе.**
Переносить надо цеховую базу `shop.db` (то, что вводят люди); база станков
пересобирается из зеркала. Все соединения создаются в `storage.py` — переезд
правит один файл. PostgreSQL, TimescaleDB, ClickHouse для 80 станков избыточны:
к ним стоит вернуться, если начнём писать посекундные датчики (натяжение, давление)
со всех станков.

**Если годовые отчёты станут ежедневными** — месячная свёртка поверх `stop_day`:
год превратится из 430 тысяч строк в 35 тысяч.

## Чтобы работало без присмотра

1. **Автозапуск** — `_deploy\install_autostart.ps1`: задание планировщика от имени
   SYSTEM, перезапуск через минуту после падения.
2. **Резервные копии** — `_deploy\backup.ps1`: `VACUUM INTO` цеховой базы раз в сутки.
3. **Журнал** — `_app\logs\app.log`, 10 файлов по 2 МБ; ошибки сборщика пишутся
   при смене, а не на каждой попытке.
4. **Проверка живости** — `/api/health`: базы, сборщик, свежесть снимка FACT,
   сколько мониторов на связи.
5. **Данные не живые — видно сразу**: снимку больше трёх минут — на доске жёлтая
   строка, через полчаса — тревога в телеграм.
6. **Закрытые данные**: без входа отдаются только адреса мониторов; зарплата,
   KPI и отчёты — после входа или по ключу API.
7. **Проверки**: `golive.py` перед подключением, `selftest.py` после обновления,
   `_tools\loadtest.py` — нагрузка.
