# Автотесты и выпуск изменений

Автотесты входят в работу над надёжностью и новым интерфейсом. Интеграция 1С
и изменение исторического учёта остаются за рамками текущего этапа; существующие
тесты этих разделов продолжаем запускать для защиты от случайных поломок.

## Что уже можно запускать

Из корня репозитория:

```text
python _tools/check.py
```

Команда запускает все `_tools/test_*.py` отдельными процессами, чтобы подмены
путей и глобальное состояние одного набора не влияли на другой. При ошибке,
тайм-ауте набора (180 секунд) или отсутствии тестов возвращает ненулевой код.
Остальные наборы продолжают выполняться, чтобы увидеть все ошибки за один запуск.
Используется тот же Python, которым запущен `check.py`.

Наборы используют временные данные и локальные тестовые HTTP-серверы. Рабочий
сервер `:8780` и оборудование FACT не используются для пишущих проверок.
Новые регрессии проверяют отчёт за период на настоящей временной SQLite:
пропущенный станок внутри заполненного дня, неизвестные килограммы, настоящий
ноль, частичный итог, несколько смен за день и пустой период. Отдельно проверены
закрытие читающего соединения при успехе и исключении и запрет записи через него.

Прохождение этой команды **не означает**, что пройдены сквозные или визуальные
проверки и что весь проект готов к выпуску.

## Пилот React

Из `frontend` выполнить `pnpm install --frozen-lockfile`, затем `pnpm check`.
Эталон — существующий HTML-отчёт, без изменения дизайна и формул. Тесты запускают
его исходный рендерер из `_app/ui.html` в отдельном DOM и сравнивают с React:
все 45 колонок, тексты, классы окраски, подсказки, итоги, фильтры, сортировку,
128 сочетаний свёрнутых групп, граничные значения порогов и оба языка чисел.
Отдельно проверяются действия пользователя и мост к существующей оболочке:
обновление данных, сохранение фильтров и введённых дат, открытие заправки,
права, вызовы периода, утверждённых отчётов, Excel и полноэкранного режима.
Затем выполняются проверка типов и сборка. Вызов обработчика в компонентном
тесте не доказывает успешное проведение документа — для этого нужен полный E2E.

Контроллер дополнительно проверяется на гонки запросов, отмену, повтор после
ошибки, истечение сессии и совместимость сохранённых настроек. Форма заправки —
на ручные значения, все места пряжи, точное время, выбор станков с той же тканью,
отмену подтверждения без потери ввода и блокировку повторного нажатия.
HTTP-тест песочницы выполняет настоящее проведение и пересчёт дневного отчёта
на временной синтетической SQLite с последующим экспортом. Проверки прав
подтверждают запрет проведения для пользователя только с доступом к отчёту.

В общий Python-запуск включены HTTP-проверки раздачи `/next/` и песочницы
нового экрана: настоящие временные SQLite, сессии, права, отчёт и причины.
Песочница и оставшиеся ограничения описаны в `frontend/README.md`.
Проверка интерфейса в настоящем браузере пока выполняется отдельно; Vitest
использует jsdom и не подтверждает правильность CSS или поведение всех браузеров.

## Проверки по мере переноса

| Уровень | Проверяемое поведение | Когда запускать |
| --- | --- | --- |
| Расчёты Python | Эталонные значения, пустые и частичные данные, нулевой выпуск | При каждой правке |
| API и права | Доступ по ролям, запрещённые действия, структура ответа отчёта | При каждой правке |
| Компоненты интерфейса | Фильтры, таблицы, состояния загрузки, ошибки, неизвестные значения | При каждой правке интерфейса |
| Сквозные сценарии в браузере | Вход; отчёт → причины → станок; сохранение периода и фильтров; выгрузка | Перед выпуском |
| Сборка | Проверка типов и успешная производственная сборка интерфейса | Перед выпуском |
| Установка выпуска | Ошибка тестов/сборки не переключает текущую версию; проверка готовности ограничена временем | При правках обновления |

Тесты компонентов должны проверять действия и видимый результат, а не внутреннюю
структуру компонентов. Эталонные суммы задаются независимо от проверяемой формулы.
Новую ошибку сначала воспроизводим тестом; после исправления он остаётся в наборе.
Для браузерных сценариев нужны устойчивые идентификаторы элементов, независимые
от перевода надписей. Скриншоты применяем к нескольким ключевым экранам с
фиксированными данными и размером окна; снимок не заменяет проверку чисел и прав.

## Песочница и обязательный сквозной тест

Правила подготовки `_tools/e2e_test.py` описаны в `AGENTS.md`. Запуск только на
отдельной копии, порт 8790, режим `--mirror --no-collector`. Рабочие конфигурации,
сессии и API-ключи не переносим. При необходимости копии БД создаём через SQLite
backup API с исходным соединением `mode=ro`. Тестовые учётные данные создаём заново.
Предпочитаем синтетические воспроизводимые данные без зависимости от меняющегося
рабочего зеркала.

Текущий E2E требует локальные `13.mxl`, `order_1557.json` и подготовленную БД.
Для повторного запуска из корня:

```text
python _tools/run_e2e.py --data-root PATH_TO_ARCHIVE --mxl PATH_TO_13_MXL --order PATH_TO_ORDER_1557_JSON --result PATH_TO_LOG_DIRECTORY
```

Скрипт создаёт временную копию кода, берёт SQLite backup из указанных архивных БД,
переносит зеркало и фикстуры, заменяет сессии и ключи тестовыми и запускает сервер
только на 127.0.0.1:8790. Конфигурация не копируется; внешние Python-соединения
запрещены. В конце сервер останавливается, копия удаляется, результаты остаются
в указанном каталоге. На Windows экспорт требует установленный Excel и шаблон,
указанный в `fill_template.ps1`; оригинал шаблона не меняется.
29.09.2026 этот прогон завершился 99 успешными проверками. Отсутствующие фикстуры
считаются ошибкой подготовки, а не успешным пропуском проверки.

## Подключение к обновлению Linux

Существующий `post-receive` уже запускает `test_*.py` перед установкой. Следующий
шаг — подключить общий запуск, сквозную песочницу и сборку интерфейса к единой
проверке кандидата. Ошибки должны сохраняться в журнале и давать ненулевой код;
переключение выпуска выполняется только после всех обязательных проверок.
Изменения хука сначала проверяются на временном Git-репозитории с подставной
командой установки. Рабочий хук этим документом не изменяется.

Готовность функции: код + тесты её поведения + успешные обязательные проверки.
Миграция интерфейса идёт по одному экрану; каждый перенос сверяем по данным,
правам и пользовательским сценариям со старым экраном.
